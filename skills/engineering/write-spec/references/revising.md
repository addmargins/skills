# Revising a spec

Come here when a spec for the intent already exists and something has changed. Someone may have answered questions in the conversation, on the answer lines in the file, or in review comments the user points to. Or the intent may have changed.

- **Only the owners close a question.** Take an answer as decided only when every owner the question names has given it. For a conflict between policies, that means both policy owners. Put a partial answer, or anyone else's answer, under the question as input, and leave the question open. When the user relays someone's answer, record both names.
- **Apply it everywhere it lands.** Write the answer into the rules, steps, and cases it settles, with the source "Q3 answer, <name>, <date>". Remove the question from Open questions and from the Reviewers table. Add a line to the Decision log, a section you add at the first answer: the question's ID and short name, the answer, who decided, the date, and where it was given. Don't copy the rule there.
- **Keep IDs stable.** Never renumber, and never reuse a removed ID, so that reviews and plans that cite R9 still point at the same rule. New items take the next unused number. After the edit, search for every removed ID and fix each reference that still treats it as open or as an existing rule. A source such as "Q3 answer, <name>, <date>" stays.
- **Look for what the answer opens.** An answer often raises a new question, or makes a new derivation possible. Sweep the affected parts again (SKILL.md step 3), and run SKILL.md step 6 again on what changed. If you read the workspace again, update `Verified against`.
- **Send intent changes back.** If an answer changes the problem, the desired outcome, or the scope, don't absorb it. Add an open question saying the intent needs revising with clarify-intent.
- **Suggest recording policy readings.** When an answer settles how a policy's words are read, suggest that its owner write that reading into the policy, so the next spec doesn't have to ask again. Never edit a policy yourself.
- **Status.** Set `Accepted (<name>, <date>)` only when two things hold: the product owner, or whoever the workspace names as accepting specs, says so, and no open question blocks planning. If they ask to accept while such questions are open, list those questions with their owners and keep the status Draft. Planning starts at acceptance. A later change to an accepted spec sets it back to Draft. If a plan already cites the spec, tell the user which IDs changed meaning.
- **Write a new spec for a superseding intent.** When a new intent supersedes this one, write a new spec for it with a `Supersedes:` line. Carry each answer recorded in the old spec's Decision log into the new spec as a source, unless the new intent changes what it decided. In that case, ask again and quote the earlier answer. In the old spec, add `Superseded by: <new file name>` as its own paragraph right after the title, and change nothing else.
