# 진행자 체크리스트

진행자는 Claude Code를 실행하고, 기록하고, 결과가 팀 밖으로 나가기 전에 익명화하는 사람입니다. 단계는 `README.md`의 진행 순서를 따릅니다.

## 시작 전

- [ ] 팀장과 제품 책임자가 파일럿에 동의했다.
- [ ] 참여자에게 무엇을 재는지 알렸고, 결과는 익명화한 뒤에만 팀 밖으로 나간다고 말했다.
- [ ] intent 1–2건을 골랐다 (README 1단계).
- [ ] 역할마다 사람을 정했다: 원 작성자, 제품 책임자, 정책마다 소유자, 기술 리드, 엔지니어 1–2명.
- [ ] Claude Code와 플러그인을 설치했다. 설치한 날과 `claude plugin details addmargins@addmargins` 결과를 적었다.
- [ ] 정책 문서가 `docs/policies/`에 있고, 문서마다 소유자가 적혀 있다.
- [ ] intent가 `docs/intents/NNNN-<slug>.md`에 있고, 원 작성자와 제품 책임자의 이름이 적혀 있다.
- [ ] 검토자마다 `reviewer-form.md`, 엔지니어마다 `engineer-log.md` 사본을 만들었다.
- [ ] 검토자에게 미리 말했다: 엔지니어에게 묻기 전에 혼자 먼저 읽을 것, 막힌 곳이 곧 결과라는 것.
- [ ] 엔지니어에게 미리 말했다: 검토자가 읽기 전에 spec을 설명해 주지 말 것.

## 진행 중

### spec 만들기
- [ ] `/write-spec`을 실행하고 적었다: 걸린 시간, 열린 질문 수, 계획을 막는 질문 수, 스킬이 보고한 검토 라운드 수, 정책 충돌.
- [ ] 초안을 손대지 않고 커밋했다. 이후 spec은 스킬로만 고친다. 손으로 고쳤다면 무엇을 왜 고쳤는지 적었다.
- [ ] 다른 사람의 질문에 대신 답하지 않았다. 대신한 답은 결정처럼 보이는 추측이 된다.

### 검토와 답
- [ ] spec과 양식을 보낸 날을 아래 질문 기록표에 적었다.
- [ ] 양식을 받으면 3번(찾은 질문 번호)을 실제 목록과 비교해, 놓친 것과 잘못 짚은 것을 셌다. 실제 목록은 spec에서 '무엇을 확인하거나 결정하면 해결되는가?'에 그 사람이나 그 역할이 나오는 질문이다.
- [ ] 답을 받으면 '답변' 줄에 적거나 대화로 전하고, 같은 `/write-spec` 명령을 다시 실행했다. 대신 전한 답은 답한 사람과 전한 사람을 함께 적었다.
- [ ] 반영할 때마다 질문 기록표를 고쳤다: 소유자가 답한 날(spec의 Decision log에 적힌 날짜), 다시 열린 횟수와 이유, 스킬이 새로 만든 질문.

### 수락과 계획
- [ ] 제품 책임자가 수락했고 spec 상태가 Accepted다. 수락한 날을 적었다.
- [ ] 엔지니어에게 로그를 시작하라고 알렸다. 계획하는 동안 일주일에 한 번 로그가 쌓이는지 확인했다.

### 질문 기록표 (spec 한 건에 한 장)

| 질문 | 소유자 (역할) | 계획을 막음 / 출시 전 | 보낸 날 | 소유자가 답한 날 | 걸린 영업일 | 다시 열린 횟수와 이유 |
|---|---|---|---|---|---|---|
| | | | | | | |

새 번호로 다시 물은 질문은 원래 질문 줄의 '다시 열린 횟수'에도 셉니다. 소유자가 두 명인 질문은 마지막 소유자가 답한 날을 적습니다. 수락 때까지 답이 없는 출시 전 질문은 '소유자가 답한 날'에 "없음"이라고 적습니다.

## 끝난 뒤

- [ ] 양식과 로그를 모두 모았다.
- [ ] 엔지니어 로그의 줄마다 기술 리드, 제품 책임자와 함께 '회고 분류'를 채웠다.
- [ ] 양식 7번(묻지 않고 정한 규칙)과 8번(빠지거나 좁아진 것)을 정책 원문과 intent에 대조했다. 원문이 실제로 정한 것이면 세지 않는다.
- [ ] 요약표를 채웠다.

| 사람 (역할) | 찾는 데 걸린 분 | 놓친 / 잘못 짚은 질문 | 질문만 보고 답함 / 내 질문 | 선택지와 맞거나 되묻지 않은 답 / 내 질문 | 이해 못 한 문장 | 묻지 않고 정한 규칙 | 승인 가능 |
|---|---|---|---|---|---|---|---|
| | | | | | | | |

  요약표 아래에 함께 적는다.
  - 원 작성자: 빠지거나 좁아진 것의 수
  - 엔지니어 로그: 진짜 빈틈(돈 / 개인정보 / 법적 의무 / 그 밖), spec에 있었음, 엔지니어링 선택의 수
  - 질문: 회신 영업일의 중앙값과 최댓값, 다시 열린 질문 수 / 전체 질문 수
  - spec: 실행 시간, 열린 질문 수, 계획을 막는 질문 수, 검토 라운드 수

- [ ] 회고를 열었다. 순서:
  1. 요약표를 함께 본다.
  2. 진짜 빈틈을 하나씩 본다: 누가 정했어야 했나, spec의 어디에 있었어야 했나.
  3. 이해하지 못한 문장과 묻지 않고 정한 규칙을 본다.
  4. 다시 열린 질문과 오래 걸린 회신의 이유를 본다.
  5. 다음 할 일을 정한다: 스킬 변경 후보(README의 표), fixture 후보, 팀 밖으로 보낼 것과 보내지 않을 것.

## 팀 밖으로 보내기 전: 익명화

무엇이든 팀 밖으로 나가기 전에 모두 끝냅니다. 요약표 한 장만 보내더라도 마찬가지입니다.

- [ ] 보낼 파일만 저장소 밖의 새 폴더에 복사했다. git 기록에 원래 내용이 남아 있으므로 저장소나 `.git`째로 보내지 않는다.
- [ ] 사람 이름을 역할 이름으로 바꿨다 (예: "재무 정책 소유자"). 같은 사람은 모든 파일에서 같은 이름이다. 원래 이름과의 대응표는 팀 안에만 둔다.
- [ ] 회사, 제품, 고객, 협력사 이름과 이메일, 전화번호, 계좌, 내부 URL과 서버 이름, 티켓과 문서 번호, 비밀값(키, 토큰)을 지웠다.
- [ ] 실제 고객 사례와 개인정보, 공개되지 않은 가격이나 매출 같은 숫자를 지어낸 값으로 바꿨다. 숫자를 바꿨으면 intent, 정책, spec의 사례 표에서 그 숫자를 모두 같이 바꾸고, 계산과 기준값의 앞뒤 관계(넘는지, 못 미치는지)가 그대로인지 확인했다.
- [ ] 정책을 바꿔 썼다면, 두 가지로 읽히는 문구와 정책 사이의 충돌은 그대로 남겼다. fixture로 쓸 때 시험하는 부분이다.
- [ ] 코드는 spec의 Facts and sources에 나온 파일만 남기고, 회사를 드러내는 이름을 바꿨다.
- [ ] 양식과 로그의 자유 서술에서 동료에 대한 평가와 사적인 말을 지웠다.
- [ ] 원래 이름과 단어를 한 줄에 하나씩, 빈 줄 없이 적은 목록(팀 안에만 둠)으로 내보낼 폴더를 검색해 0건을 확인했다: `grep -rniF -f <원래-단어-목록> <내보낼-폴더>`
- [ ] 진행자가 아닌 팀원 한 명이 다시 읽었고, 팀장이 승인했다. 회사에 외부 공유 절차(보안, 법무 검토)가 있으면 그것을 따랐다.
