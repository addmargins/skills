# write-spec 파일럿 키트

실제 팀이 자기 일 1–2건에 write-spec 스킬을 직접 써 보고, 에이전트 역할극으로는 잴 수 없는 것을 잽니다.

## 목적

write-spec은 intent(의도 문서)를 spec으로 바꿉니다. spec에는 무엇을 만들지와 지켜야 할 정책이 들어갑니다. 아직 아무도 정하지 않은 것은 정할 사람 앞으로 열린 질문(Q1, Q2 …)으로 남깁니다. spec을 검토하는 사람은 대부분 코드를 읽지 않습니다.

지금은 이것을 에이전트로만 확인합니다. 역할극(`../plan.md`의 T5, `../graders/t5-roleplay-procedure.md`)에서는 에이전트가 원 작성자와 정책 소유자를 연기합니다. litmus 감사(`../graders/litmus-reader.md`)에서는 에이전트가 spec만 보고, 혼자 정해야 하는 것을 적습니다. 이 파일럿은 같은 것을 실제 사람으로 잽니다.

- 엔지니어가 아닌 검토자가 자기 부분을 찾고, 이해하고, 자기 질문에 답할 수 있는가
- 수락된 spec으로 계획하는 엔지니어가 그래도 혼자 정해야 하는 것은 무엇인가 (litmus 감사의 실제 버전)
- 질문에 답이 오기까지 얼마나 걸리고, 답을 받고도 다시 열리는 질문은 몇 개인가

## 키트 구성

| 파일 | 누가 | 언제 |
|---|---|---|
| `README.md` | 팀장, 진행자 | 시작 전 |
| `reviewer-form.md` | 검토자 한 명이 spec 한 건에 한 장 | 검토할 때 |
| `engineer-log.md` | 엔지니어 한 명에 한 부 | 수락 뒤 계획할 때 |
| `facilitator-checklist.md` | 진행자 | 처음부터 끝까지, 익명화 포함 |

팀장은 '무엇을 재나요'까지만 읽으면 됩니다. 마지막 두 절은 스킬을 관리하는 쪽을 위한 것입니다.

## 누가 참여하나요

| 역할 | 누구 | 하는 일 |
|---|---|---|
| 진행자 | 팀에서 한 명. Claude Code를 실행합니다 | 설치, 실행, 일정, 기록, 회고, 익명화 |
| 원 작성자 | 이 일을 요청한 사람 | intent 만들기. spec이 처음 문제를 푸는지, 빠진 것은 없는지 검토 |
| 제품 책임자 | 범위와 제품 동작을 정하는 사람 | 자기 질문에 답하기, spec 수락 |
| 정책 소유자 | 이 일이 닿는 정책마다 그 정책의 담당자 | 자기 정책에 관한 규칙과 질문 검토 |
| 기술 리드 | 이 일의 기술 책임자 | spec의 사실 목록(Facts and sources) 확인 |
| 엔지니어 1–2명 | 이 일을 실제로 계획할 사람 | spec 검토, 수락 뒤 엔지니어 로그 |

원 작성자와 정책 소유자는 엔지니어가 아닐수록 좋습니다. 이 파일럿에서 가장 중요한 사람들입니다.

## 설치와 실행

진행자 컴퓨터에 Claude Code가 있어야 합니다. 설치는 Claude Code 공식 문서를 따르세요. 검토자는 아무것도 설치하지 않습니다.

터미널에서 플러그인을 설치합니다.

```bash
claude plugin marketplace add addmargins/skills
claude plugin install addmargins@addmargins
```

Claude Code 안에서라면 `/plugin marketplace add addmargins/skills`, `/plugin install addmargins@addmargins`를 입력합니다. 설치되었는지는 `claude plugin details addmargins@addmargins`로 확인합니다.

팀 저장소 루트에서 `claude`를 실행한 뒤 이렇게 부릅니다.

```text
/clarify-intent <요청을 한두 문장으로>
/write-spec docs/intents/NNNN-<slug>.md
```

- 다른 명령과 이름이 겹치면 `/addmargins:clarify-intent`, `/addmargins:write-spec`으로 부릅니다.
- 두 스킬은 저절로 실행되지 않습니다. 꼭 슬래시 명령으로 부르세요.
- clarify-intent는 `docs/intents/NNNN-<slug>.md`를 만듭니다. write-spec은 그 옆 `docs/specs/`에 같은 이름의 spec을 만듭니다. intent가 한국어면 spec 본문도 한국어이고, 섹션 제목은 영어로 남습니다.
- spec이 이미 있을 때 같은 `/write-spec` 명령을 다시 실행하면, 새로 쓰지 않고 그 spec을 고칩니다. 답을 반영할 때 이렇게 씁니다.
- 파일럿 중에는 플러그인을 업데이트하지 마세요. 이 마켓플레이스의 자동 업데이트는 기본으로 꺼져 있습니다.

## 진행 순서

1. **intent 고르기.** 곧 실제로 만들 일 1–2건을 고릅니다. 돈, 개인정보, 법적 의무 중 하나 이상에 닿고, 글로 된 정책이 하나 이상 있고, 원 작성자와 제품 책임자가 정해져 있으면 좋습니다. 이미 설계나 명세가 나온 일은 피합니다.
2. **intent 만들기.** 원 작성자가 옆에서 직접 답하고, 진행자가 `/clarify-intent`를 실행합니다. 요청서가 이미 있으면 그 내용을 붙여 넣고 시작해도 됩니다. 원 작성자와 제품 책임자의 이름과 역할을 intent 본문에 적어 둡니다. 스킬은 문서에 적힌 이름만 씁니다.
3. **정책 모으기.** 이 일에 닿는 정책 문서를 저장소의 `docs/policies/`에 넣고, 문서마다 머리말에 소유자를 적습니다. 위키에만 있는 정책은 스킬이 읽지 못합니다.
4. **spec 만들기.** `/write-spec docs/intents/NNNN-<slug>.md`를 실행합니다. 스킬이 마지막에 알려 주는 열린 질문 수, 계획을 막는 질문, 정책 충돌을 적고, 초안을 손대지 않은 채 커밋합니다. 진행자는 다른 사람의 질문에 대신 답하지 않습니다.
5. **검토.** 검토자마다 spec과 `reviewer-form.md`를 보내고 보낸 날을 적습니다. 검토자는 엔지니어에게 묻기 전에 혼자 읽고 양식을 채웁니다.
6. **답 반영.** 검토자는 답을 spec의 '답변' 줄에 적거나 진행자에게 보냅니다. 진행자는 같은 `/write-spec` 명령을 다시 실행해 반영합니다. 대신 전하는 답은 누가 답했고 누가 전했는지 함께 말합니다. spec은 스킬로만 고칩니다.
7. **수락.** 계획을 막는 질문이 모두 닫히면 제품 책임자가 수락합니다. 그 사실을 스킬에 전하면 상태가 Accepted로 바뀝니다. 막는 질문이 남아 있으면 스킬은 수락하지 않고 그 질문들을 보여 줍니다.
8. **계획.** 엔지니어는 평소처럼 구현 계획을 세우면서, 혼자 정해야 했던 것을 `engineer-log.md`에 한 줄씩 적습니다.
9. **회고.** 진행자가 양식과 로그를 모아 요약표를 만들고 로그의 줄마다 분류합니다. 그다음 참여자와 회고합니다(`facilitator-checklist.md`).
10. **넘기기.** 무엇이든 팀 밖으로 보내기 전에 익명화를 끝냅니다(`facilitator-checklist.md` 마지막 절).

## 무엇을 재나요

| 역할 | 재는 것 | 기록하는 곳 | 역할극과 같은 기준 |
|---|---|---|---|
| 모든 검토자 | 자기 부분을 찾는 데 걸린 시간, 놓치거나 잘못 짚은 질문 | 검토 양식 2–4 | 1분 안에, 찾은 목록이 실제 질문과 일치 |
| 모든 검토자 | 질문 글만 보고 답할 수 있었던 질문 / 내 질문 | 양식 5 | 90% 이상 |
| 모든 검토자 | 답이 선택지 하나와 맞거나 되묻지 않고 반영된 질문 / 내 질문 | 양식 5, 질문 기록표 | 90% 이상 |
| 모든 검토자 | 엔지니어 없이 이해하지 못한 문장 | 양식 6 | 한 사람에 2개 이하, 자기 질문 안에는 0개 |
| 모든 검토자 | 묻지 않고 내 영역을 정해 버린 규칙 | 양식 7 | 0개 |
| 원 작성자 | intent에서 빠지거나 좁아진 것 | 양식 8 | 0개 |
| 엔지니어 | 수락 뒤 계획하면서 혼자 정해야 했던 것 | 엔지니어 로그 | 진짜 빈틈 중 돈·개인정보·법적 의무 0개, 그 밖 1개 이하 |
| 진행자 | 질문별 회신 시간, 다시 열린 질문 수 | 체크리스트의 질문 기록표 | 기준 없음 (처음 재는 것) |

기준은 `../plan.md`의 T5 단언과 litmus 기준(T3.7)을 그대로 옮겼습니다. 같은 기준을 쓰면 실제 결과를 역할극 결과와 나란히 놓을 수 있습니다. spec마다 실행 시간, 열린 질문 수, 계획을 막는 질문 수, 스킬이 보고한 검토 라운드 수도 적습니다.

- **회신 시간:** 질문이 담긴 spec을 소유자에게 보낸 날부터 소유자가 답한 날(spec의 Decision log에 적히는 날짜)까지의 영업일. 소유자가 두 명인 질문은 마지막 소유자가 답한 날까지입니다.
- **다시 열린 질문:** 답을 받은 뒤 같은 점을 다시 물어야 했던 질문. 답이 모호했거나, 다른 소유자의 답이 더 필요했거나, 계획 중에 답이 모자란 것으로 드러난 경우입니다. 스킬이 새 번호로 다시 물은 것도 셉니다.
- **진짜 빈틈:** spec이 정하지도 묻지도 않았는데, 엔지니어가 아닌 누군가가 정했어야 하는 것. 회고 전에 진행자가 기술 리드, 제품 책임자와 함께 로그의 줄마다 가립니다.
- **묻지 않고 정한 규칙:** 정책 문구나 intent가 실제로 정해 둔 것이면 세지 않습니다. 진행자가 원문과 대조합니다.

## 결과를 스킬 변경으로 (스킬 관리자용)

팀은 익명화한 요약표, 양식, 로그만 넘기면 됩니다. 아래는 스킬을 관리하는 쪽의 일입니다. 경로는 이 저장소 루트 기준입니다.

| 결과 | 먼저 볼 곳 (`skills/engineering/write-spec/`) |
|---|---|
| 자기 질문을 못 찾거나 오래 걸림, 질문이 엉뚱한 사람에게 감 | `SKILL.md` 5단계 Reviewers, `references/spec-template.md` |
| 질문 글만으로 답하지 못함, 답이 선택지 밖 | `references/open-questions.md`의 필드와 선택지 |
| 엔지니어 없이 이해하지 못한 문장 | `SKILL.md` 5단계의 쓰기 규칙 |
| 묻지 않고 정한 규칙 | `SKILL.md` 원칙 "Settle nothing that isn't settled", 3–4단계 |
| intent에서 빠지거나 좁아진 것 | `SKILL.md` 2단계 목록, 6단계 점검 2 |
| 엔지니어 로그의 진짜 빈틈 | `SKILL.md` 3단계 빈틈 목록. 어느 항목에 들어가는지 보고, 없으면 새 항목 후보 |
| 다시 열린 질문 | `references/open-questions.md`, `references/revising.md` |
| 회신이 느림 | 질문 수와 분류: `SKILL.md` 4단계, `references/open-questions.md`의 Classes |

1. 한 사람의 취향보다 여러 검토자에게서 되풀이된 것, 그리고 돈·개인정보·법적 의무에 닿은 빈틈을 먼저 다룹니다.
2. 변경 제안마다 근거가 된 양식이나 로그의 줄(익명화한 것)을 붙입니다.
3. 역할극이 놓친 것이면 역할극도 고칩니다: `evals/write-spec/plan.md` T5의 페르소나 입장과 단언, `evals/write-spec/graders/t5-roleplay-procedure.md`.
4. 스킬을 바꾼 뒤에는 하네스(`evals/write-spec/README.md`)를 다시 돌리고 `plan.md` §4 기준을 확인합니다.

## 새 회귀 fixture 만들기 (스킬 관리자용)

파일럿 intent와 그 spec은 이름과 민감한 내용을 지운 뒤 `evals/write-spec/fixtures/` 아래 새 fixture가 될 수 있습니다. 정답 키는 엔지니어 로그로 만듭니다. 그 전에 `facilitator-checklist.md`의 익명화를 끝냅니다.

- **fixture** `fixtures/<이름>/`: 익명화한 `README.md`, `docs/intents/`, `docs/policies/`, 그리고 spec의 Facts and sources에 나온 코드 파일만 넣습니다. `ho-*` fixture와 같은 모양입니다. 첫 초안을 시험하려면 `docs/specs/`를 빼세요. 있으면 스킬이 새로 쓰지 않고 고칩니다. 실제 답으로 고치기를 시험하려면 spec과 답을 넣어 `t1-acme-revise`, `t7-ledgerly-answers`처럼 만듭니다.
- **정답 키** `keys/<이름>.md`: `keys/ho-*.md`의 구조(사람과 소유자, 코드에서 찾을 사실, 충돌, 두 가지로 읽히는 조항, 빈틈, 미끼)를 따릅니다. 엔지니어 로그의 '진짜 빈틈' 한 줄이 빈틈 하나(G1, G2 …)가 되고, 그 줄의 '누가 정했어야 하나'와 '돈 / 개인정보 / 법적 의무'가 소유자와 영역이 됩니다. 파일럿 spec이 이미 물었던 질문과 검토자가 찾은 '묻지 않고 정한 규칙'도 빈틈이나 두 가지로 읽히는 조항으로 넣습니다. 'spec에 있었음'으로 가른 줄은 미끼 후보입니다. 익명화한 파일럿 spec은 비교 기준으로 키 옆에 둡니다. 실행은 `keys/`를 보지 못합니다.
- **채점:** `cases.md`에 실행 프롬프트 한 줄을 더하고 `graders/task-held-out.md`로 채점합니다.
- 이 키는 스킬 변경을 이끌었으므로 held-out이 아니라 회귀용입니다.
